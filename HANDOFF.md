### Design

Content flags come from `document_scenes.data->>'type'` (`quiz`; `interactive` or `pbl`) in the same query that counts scenes. `updatedAt` is the approval time (`course_shares.decided_at`) for a shared course, because readers see the approved copy, and `document_stages.updated_at` (milliseconds) for the others. All three are absent when the course documents are not stored here. Additive fields, old clients ignore them.
- Client: new filters `has=quiz,interactive` (a course must have every chosen one) and `len=short,medium,long` (at most 5 scenes, 6 to 15, more than 15; a course of unknown length matches none), sort `updated`, layout `layout=list` (compact rows). The default sort stays A to Z so the order of an existing catalog does not change.

- Discussion: `lib/hooks/use-discussion-tts.ts`. A failed cloud segment (generation error, play rejected, audio `error` event) goes to the browser instead of being skipped. - Tests: `tests/playback/speech-browser-fallback.test.ts` (new, 4 tests); `tests/hooks/use-discussion-tts.test.ts` (4 new tests appended).

### Decisions and reasons
- Keep the `ttsEnabled` gate in both paths. If the user turned TTS off, silence is intended.
- Lecture and discussion both ignore the browser-native `enabled` toggle on the fallback path. Its default is `false` (`lib/store/settings.ts:528`), so the old gate never fired for a default user, which is the reported symptom. The owner asked for the fallback regardless of settings. This overrides the #665 opt-in for the fallback path only. Choosing browser-native directly works as before.
- Discussion with no enabled provider now speaks with the browser when `ttsEnabled` is on. The old rule "no silent browser-native" (`use-discussion-tts.ts:416`) was removed. Without speech synthesis the segment is skipped, and the queue still advances.
- A retried segment (browser fallback or clone fallback) is not counted in `segmentDoneCounterRef`. The stream buffer holds for TTS on that counter, so counting early would release the hold while the browser is still speaking.
- Browser speech for the fallback uses the cloud voice id as `voiceURI`. It does not match a browser voice, so the browser's default voice is used. Matching the lecture fallback.

### Design

**Notifications (rows 2–3)**
- N1 Table `notifications (id BIGSERIAL, account_id → accounts ON DELETE CASCADE, kind TEXT, ref TEXT, count INT DEFAULT 1, data TEXT (JSON), created_at, updated_at, read_at NULL, UNIQUE (account_id, kind, ref) WHERE read_at IS NULL)`. Batching: an unread row with the same `(account, kind, ref)` is bumped (`count + 1`, `updated_at`, latest `data`) instead of adding a row, so "3 new answers to your question" is one item. Add to `LEARNING_SCHEMA` (insert before `render_jobs`, as the other community tables do).
- N2 Producers (call a store helper `notify(db, {accountId, kind, ref, data})` right after the existing write; never notify the actor themself): `answer` (new member or AI answer on your question → asker; ref = question id), `best` (your answer chosen → answer author, with tokens), `vote` (votes on your answer → author; at most one bump per answer per day), `challenge.result` (on `settleChallenge` → every entrant: rank, tokens), `challenge.open` (a new challenge opens → members who entered last month; optional, owner to decide), `share.decided` (share or update approved/rejected → owner, reason), `remix.shared` (a remix of your course got shared → source author), `support.reply` stays on its own dot (do not duplicate).
- N3 API: `GET /api/notifications?unread=1&limit=30`, `POST /api/notifications/read { ids?: number[], all?: true }`. Signed-in only (`community.read`).
- N4 UI: `NotificationBell` rendered beside `AccountControl` (it already sits in every top bar), red count, popover list (icon per kind, one line, relative time, link to the thing), opening the popover marks shown items read. Poll on window focus only (no interval).

**Spaced review (rows 4–6)**
- R1 Table `review_items (id BIGSERIAL, account_id → accounts, source_kind TEXT CHECK in ('quiz','question','challenge'), source_ref TEXT, course_id TEXT NULL, scene_id TEXT NULL, card TEXT (JSON snapshot: prompt, options, answer, explanation, link), box INT 0..5, due_at TIMESTAMPTZ, last_result TEXT NULL, reviews INT, created_at, UNIQUE (account_id, source_kind, source_ref))`.
- R2 Scheduler (pure, `lib/learning/review-schedule.ts`, unit-tested): Leitner boxes with intervals [1, 3, 7, 14, 30] days; "remembered" → box + 1 (box 5 = mastered, leaves the daily queue), "not yet" → box 0, due tomorrow. Due time is the start of the learner's local day (pass the time-zone offset from the browser).
- R3 API: `GET /api/review/today` (due cards up to the daily cap, plus counts: due, done today, next due date), `POST /api/review/items` (add cards; body capped; card fields length-capped), `POST /api/review/[id]/answer { result: 'remembered' | 'notYet' }`. Setting `review.dailyCards` (int 3..30, default 10, staff) in `lib/server/learning/settings.ts`.
- R4 Sources: (a) quiz: when an attempt reaches `reviewed` with wrong questions, the browser posts those questions as cards (the browser holds the question text, options, answer and analysis; the server checks the viewer can read the course with `canReadClassroom`; a learner can only pollute their own list); hook the place `lib/quiz/runtime.ts` writes the reviewed phase. (b) community: when the asker's question gets a best answer, the server adds a card "Your question: …" whose answer is the best answer. (c) challenge: when an entry is settled with `ai_score < 7`, the server adds a card with the problem and the reference solution. Self-check only (show answer, learner rates); no AI cost in v1.
- R5 UI: `/review` in the visitor frame: one card at a time (prompt → "Xem đáp án" → "Nhớ rồi" / "Chưa nhớ"), progress "3/10", math through `RichText` (`components/community/community.tsx`). After the cap: closing screen "Xong phần hôm nay" with what was reviewed and the next due date; an explicit "Ôn thêm 5 thẻ" button is the only way to continue. Home card "Ôn lại hôm nay: N thẻ" when N > 0.

**Weekly goal and recap (row 7)**
- W1 Table `learning_goals (account_id PK, days_per_week INT 1..7, updated_at)`; default none (the learner opts in).
- W2 Table `learning_days (account_id, day DATE, kinds TEXT[], PRIMARY KEY (account_id, day))`, upserted by the server routes that represent learning: review answer, community answer, challenge entry, plus `POST /api/activity { kind: 'scene' | 'quiz' }` from the classroom when a scene is completed or a quiz submitted (one call per scene, idempotent per day).
- W3 Recap (computed on read, no job): days learned this week vs goal, cards reviewed and share remembered, questions answered and best answers, challenge result, tokens earned this week, badges; compared with last week. "Weeks in a row meeting your goal" is shown when ≥ 2 and silently restarts otherwise (no warnings, no loss messages). Shown on the home and in the community page header.

**Progress and profile (row 8)**
- P1 Per-course mastery: share of quiz questions whose latest attempt is correct, plus review cards in box ≥ 3; a simple bar per course the learner opened. Topic-level mastery needs topic tags on questions; out of scope.

### Design

Access request (registration is public, so the administrator cannot tell a stranger from a person who needs access):
- Who may ask: a signed-in learner whose membership is not active (none, or expired). A suspended membership gets no button: the administrator paused it on purpose. Staff never ask.
- Learner view, in the composer's locked slot: the reason, a button, an optional note of at most 280 characters. After sending: "request sent on <date>". After a rejection: "not accepted; you can ask again after <date>" (24 hours later). When approved, the membership appears and the status strip shows it. No push or email.
- One row per account (`access_requests`, primary key `account_id`): asking again updates it. One pending request at a time.
- Operator view: panel "Access requests" under the members panel: username, note, date, membership state. Approve grants the defaults used by the members panel (30 days, `DEFAULT_MONTHLY_QUOTA_TOKENS`) in one transaction with an audit row; Reject takes an optional reason (at most 200 characters) and writes an audit row. The summary strip gets a fourth count.
- Permissions: new policy action `access.request` and capability flag `requestAccess`; deciding uses the existing `membership.manage`.
- Routes: `GET` and `POST /api/membership/request` (learner); `GET /api/admin/access-requests` and `POST /api/admin/access-requests/[accountId]` (staff). New error codes: `ALREADY_MEMBER`, `REQUEST_PENDING`, `REQUEST_TOO_SOON`, `MEMBERSHIP_SUSPENDED`. The interface maps codes to translated text (`learning.errors.*`), as the server never sends text to show.

My contribution (`GET /api/membership/contribution`, block under "My classes", for anyone who may share): the learner's shared courses with state (pending or shared) and readers per course, total distinct readers, bonus tokens this month against `MONTHLY_REWARD_CAP_TOKENS`, earned badges (`readBadges`, never called today), and how many readers are missing for the next badge (`BADGE_THRESHOLDS`). The block is hidden when there is nothing to show.

Learning focus: two free-text fields (subject, level; at most 40 characters each) stored in the existing profile store (`lib/store/user-profile.ts`, the same store as nickname and bio, so it gets whatever sync those get). Shown as a one-line chip under the composer with an inline editor. The generator receives it: `app/page.tsx` already sends `userBio`; the text now ends with the subject and level through a pure helper. Starter prompts stay generic; subject-specific suggestions are not part of wave 2.

Not in wave 2 (do not build): push or email notices, subject picker lists, subject-specific suggestions, leaderboards, payments.

Proposed by the agent, not decided by the owner (rows stay Blocked until the owner says yes): titles for class courses; a resume position that follows the learner across devices.
